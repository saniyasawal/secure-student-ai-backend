# Secure Student Records & Academic Insights AI — Backend

A security-focused REST API built with **Python and FastAPI** to provide student academic records, academic performance insights, and teacher-level class summaries.

The backend is deployed on **Google Cloud Run**. It demonstrates API-key authentication, bearer-token-based user identification, role-based access control (RBAC), request validation, and secret management using **Google Cloud Secret Manager**.

The project uses a synthetic dataset of 100 student records for educational demonstration.

## Project Overview

Secure Student Records & Academic Insights AI is an academic project that demonstrates how a REST API can protect student records and expose role-appropriate academic information.

The backend is responsible for the application's security decisions. It verifies the application API key, resolves the user's bearer token, checks the user's role and permissions, validates request parameters, and returns the permitted data.

The application supports two roles:

- **Student:** Can access their own academic record and study insights.
- **Teacher:** Can access class-level academic summaries.

The backend uses a JSON file containing synthetic student records. Academic recommendations are produced using transparent rule-based logic. They are not generated by a trained machine-learning model.

## Objectives

The main objectives are to:

1. Develop a REST API using FastAPI.
2. Implement API-key authentication for trusted application-to-backend requests.
3. Implement bearer-token-based user identification.
4. Enforce role-based access control for student and teacher operations.
5. Prevent students from accessing other students' records.
6. Validate request parameters using FastAPI's validation mechanisms.
7. Store deployment secrets in Google Cloud Secret Manager.
8. Deploy the API on Google Cloud Run.
9. Demonstrate security testing using valid and invalid requests.
10. Minimize deployment costs through serverless hosting and controlled scaling.

## Features

### Student Records

The backend stores synthetic records with fields including:

- Student ID.
- Student name.
- Python marks.
- Machine Learning marks.
- Cloud Computing marks.
- Attendance percentage.

The demonstration dataset contains 100 records, identified from `S1001` to `S1100`.

### Academic Insights

The API calculates an overall academic average and compares subject marks with a requested target. It identifies subjects that require improvement and returns a corresponding study recommendation.

### Teacher Class Summary

The teacher-only endpoint returns class-level information, including the number of students and a list of student performance summaries.

### API-Key Authentication

Protected application requests require a valid API key supplied in the `X-API-Key` header.

### Bearer-Token Authentication

Record-access requests use a bearer token in the `Authorization` header. The backend maps the token to the corresponding user identity and role.

### Role-Based Access Control

Students are restricted to their own records. Teacher-only operations require the teacher role.

### Input Validation

FastAPI validates supported request parameters. Invalid values are rejected rather than silently accepted.

### Secret Management

The deployed application receives its API key and user-token configuration through Google Cloud Secret Manager, avoiding the need to commit these values to the source repository.

## Security Model

The application demonstrates multiple layers of security.

### 1. API-Key Authentication

The API key authenticates requests from the trusted application layer.

Requests must supply the expected value through:

```http
X-API-Key: <api-key>
```

The backend rejects requests that do not satisfy the configured API-key check.

An API key alone does not establish that a user is authorized to view a particular student record.

### 2. Bearer-Token Authentication

The user token is supplied through:

```http
Authorization: Bearer <user-token>
```

The backend resolves the token to a configured identity and role.

The implementation uses demonstration tokens for student and teacher access. These are suitable for a controlled academic demonstration, not production identity management.

### 3. Role-Based Access Control

After resolving the identity, the backend verifies whether the requested operation is permitted for that role.

For example:

- A student can retrieve their own record.
- A student cannot retrieve another student's protected record.
- A student cannot access the teacher-only class summary.
- A teacher can retrieve the class summary.

The backend must perform these checks independently of any frontend role selection or URL.

### 4. Input Validation

FastAPI validates request parameters before processing the relevant operation.

For example, an invalid `target_marks` value should be rejected by the endpoint's configured validation rules.

### 5. Secret Manager

In the deployed environment, the following secrets are configured in Google Cloud Secret Manager:

- `student-ai-api-key`
- `student-ai-user-tokens`

The Cloud Run service uses a dedicated runtime service account with secret-access permissions granted to the required secrets.

### 6. Public Cloud Run Ingress

The Cloud Run service is configured to accept requests at the service URL. Application-level API-key and bearer-token checks enforce the demonstrated access rules.

**Important distinction:** Cloud Run's infrastructure-level unauthenticated invocation setting is not the same as allowing unauthenticated access to protected application data. The application must continue to enforce its own authentication and authorization controls.

For production use, consider private Cloud Run ingress or IAM-based invocation where appropriate, alongside a secure authentication design.

### Example: Security Status

The security status endpoint reports configuration indicators, such as whether API-key authentication, bearer-token authentication, RBAC, and input validation are enabled.

It can also report the number of student records and configured demonstration tokens.

The endpoint must not return the actual API key, bearer tokens, or other secret values.

## Academic Insights Logic

The academic insights endpoint uses transparent, rule-based processing.

The current implementation:

1. Retrieves the permitted student's subject marks.
2. Calculates the overall average.
3. Compares each subject mark with the requested target.
4. Identifies subjects below the target.
5. Generates a recommendation naming subjects requiring revision.
6. Returns the results as JSON.

Example response structure:

```json
{
  "student_id": "S1001",
  "subject_marks": {
    "Python": 49,
    "Machine Learning": 38,
    "Cloud Computing": 70
  },
  "overall_average": 52.33,
  "target_marks": 75,
  "subjects_below_target": [
    "Python",
    "Machine Learning",
    "Cloud Computing"
  ],
  "recommendation": "Focus revision on: Python, Machine Learning, Cloud Computing",
  "note": "Recommendations are generated using transparent rules, not a trained machine-learning model."
}
```

The values above illustrate the response format using demonstration data. Results depend on the actual record and requested target.

This component is not a trained machine-learning model. Its purpose is to demonstrate academic analysis and recommendations through an API.

## Local Installation

### 1. Clone the repository

```bash
git clone https://github.com/YOUR-USERNAME/secure-student-ai-backend.git
cd secure-student-ai-backend
```

Replace `YOUR-USERNAME` with your GitHub username.

### 2. Create a virtual environment

On Windows Command Prompt:

```bat
python -m venv .venv
.venv\Scripts\activate
```

On macOS or Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Install dependencies

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

The dependencies include:

```text
fastapi
uvicorn[standard]
python-dotenv
```

### 4. Configure local environment variables

Create a `.env` file in the repository root. Use only authorized local demonstration credentials.

The exact environment variables and formats must match the implementation in `app/main.py`. The application uses `API_KEY` and may use `USER_TOKENS_JSON` for its configured user-token map.

Example template:

```dotenv
API_KEY=REPLACE_WITH_A_LOCAL_DEMO_KEY
USER_TOKENS_JSON={"student-demo-token-1001":{"student_id":"S1001","role":"student"}}
```

This is a template, not a production credential configuration. Verify the expected token-map format in the application source before using it.

Never commit `.env` to GitHub. The `.gitignore` file is configured to exclude it.

### 5. Start the API

```bash
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

The local API is available at:

```text
http://127.0.0.1:8000
```

FastAPI's interactive API documentation is normally available at:

```text
http://127.0.0.1:8000/docs
```

Protected endpoints still require the configured credentials.

## Security Testing

The following security tests were performed during the project demonstration.

| Test case | Expected result | Observed result |
|---|---|---|
| Request security status without an API key | `401 Unauthorized` | Passed |
| Student retrieves their own record with valid credentials | `200 OK` | Passed |
| Student attempts to retrieve another student's record | `403 Forbidden` | Passed |
| Student attempts to retrieve the teacher class summary | `403 Forbidden` | Passed |
| Teacher retrieves the class summary with valid credentials | `200 OK` | Passed |

Additional tests to run include:

- Invalid API key.
- Missing bearer token.
- Invalid bearer token.
- Invalid `target_marks`.
- Malformed requests.
- Attempts to bypass access checks by changing student IDs.
- Verification that secret values never appear in API responses.

Expected status codes for the relevant implemented checks include:

- `200 OK`: Successful authorized request.
- `401 Unauthorized`: Missing or invalid credentials.
- `403 Forbidden`: Authenticated identity lacks permission.
- `422 Unprocessable Entity`: Request parameters fail validation.

### Deployment Process

The deployment process includes:

1. Preparing the FastAPI application and dependency file.
2. Defining the container image through the Dockerfile.
3. Enabling the necessary Google Cloud APIs.
4. Creating a dedicated Cloud Run runtime service account.
5. Storing the API key and token map in Secret Manager.
6. Granting the runtime identity access to the required secrets.
7. Deploying the application to Cloud Run.
8. Verifying the health endpoint and protected API requests.

A typical deployment command, when the appropriate Google Cloud resources and secret versions already exist, is:

```bash
gcloud run deploy secure-student-ai-api \
  --source . \
  --project=YOUR_GCP_PROJECT_ID \
  --region=asia-south1 \
  --service-account=YOUR_RUNTIME_SERVICE_ACCOUNT \
  --set-secrets=API_KEY=student-ai-api-key:2,USER_TOKENS_JSON=student-ai-user-tokens:1 \
  --allow-unauthenticated \
  --max=2 \
  --min=0 \
  --memory=512Mi \
  --cpu=1 \
  --concurrency=80
```

Replace the project ID and service account with the appropriate values for your environment. Confirm the secret names and versions before running this command.

The `--allow-unauthenticated` setting permits requests to reach the service URL at the Cloud Run invocation layer. The application must still enforce its API-key and user authorization checks. Use a more restrictive invocation design if required by your threat model.

This command is provided for reproducibility; it should not be run blindly against an existing service.

## Secret Manager Configuration

The deployed application uses Google Cloud Secret Manager for its sensitive configuration.

The configured secret names are:

- `student-ai-api-key`
- `student-ai-user-tokens`

A dedicated runtime service account is used to access these secrets. Access is granted to the required secrets rather than broadly exposing secrets to unrelated identities.

Benefits include:

- Separation of application code and sensitive configuration.
- Reduced risk of accidentally committing credentials.
- Centralized secret storage.
- IAM-controlled access to secret values.
- Support for secret versioning and rotation.

The actual secret values must never be included in this repository or its README.

## Operational and Cost Considerations

Cloud Run is a serverless platform that can scale based on incoming requests.

The demonstration deployment uses:

- Minimum instances set to zero.
- Maximum instances limited to two.
- A single vCPU.
- 512 MiB of memory.

These settings help limit resource usage for a small educational workload. Actual charges depend on request volume, execution time, resource configuration, and other Google Cloud services.

Secret Manager, Artifact Registry, Cloud Storage, and other supporting resources may also have costs or retention implications. Review the Google Cloud Billing dashboard and clean up unused resources when the project is no longer required.

## Limitations

- The project uses synthetic student records rather than a production database.
- The demonstration token map is not a replacement for a production identity provider.
- Academic recommendations use rule-based logic, not a trained machine-learning model.
- The project does not implement institutional single sign-on or a complete account-management system.
- The current dataset is stored in a JSON file and is not designed for concurrent multi-user data modification.
- Production deployments would require additional monitoring, auditing, rate limiting, and security hardening.
- Public accessibility of the Cloud Run URL means application-level authentication remains essential.
